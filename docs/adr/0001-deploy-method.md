# ADR-0001. Деплой одной командой по SSH

- Статус: принято
- Дата: 2026-11-23

## Контекст

TimeCapsule крутится на одном EC2 (`webserver`): nginx, PHP-FPM и PostgreSQL на одной машине. Код живёт в публичном репозитории `timecapsule`, сервер только читает его по HTTPS. Новую версию надо выкатывать часто и без ручных ошибок. Ещё нужен быстрый и простой откат, если новая версия окажется с ошибкой.

## Решение

Беру `deploy.sh` в корне репозитория. На сервере он лежит как `~/deploy.sh`, запускается с ноутбука одной командой: `ssh -i ~/.ssh/ivanbordeniuc-keypair.pem ec2-user@<IP> ./deploy.sh`. Скрипт делает `git pull --ff-only`, `composer install`, `php bin/init-db.php`, `reload php-fpm` и дёргает `/health`.

Почему так: четыре команды в фиксированном порядке не забыть нельзя, а `--ff-only` не даст выложить код, который кто-то правил руками на сервере. Откат тоже идёт через репозиторий: `git revert`, push, тот же `deploy.sh`.

## Рассмотренные альтернативы

- `scp` файлов: непонятно, какая версия на сервере, легко забыть файл, отката нет.
- `git pull` руками на сервере: версия понятна, но шаги каждый раз набираются заново, composer и init-db можно пропустить.
- CI/CD (GitHub Actions и т.п.): правильное направление, но сейчас один сервер и один человек, настройка дороже выгоды. Вернусь к этому позже в курсе.

## Последствия

Что получили:

- Один способ выкатки и один способ отката, версия на сервере всегда видна в последней строке вывода.
- Сервер ничего не может записать в репозиторий, даже если его взломают.

Чем платим:

- Во время `git pull` посетитель может поймать полупереключённый код: окна простоя без атомарной смены релиза никто не гарантирует.
- `/health` проверяет только PHP и базу, сломанную главную он не увидит. Деплой считается успешным, даже если сайт лежит.
- Запуск вручную с ноутбука: нужен ключ и открытый 22-й порт на мой IP. Плюс копию `deploy.sh` на сервере надо обновлять отдельно.
